## 零、修复构建（v3.0.2）：配置与充电为什么「设了没用」

**现象**：控制台读取参数时在第 82 行报「数组未闭合」，参数页与充电页整页不可用；即使页面能开，保存充电阈值后也像「没生效」。

**根因（四处叠加，前两处是这次新查到的）**：

1. 守护进程用 `toml::to_string_pretty` 输出配置，`[scene]` 的包名列表被拆成多行数组：
   ```
   reading_packages = [
       "com.dragon.read",
       ...
   ]
   ```
   而控制台按「一行一条语句」解析，读到第 82 行 `reading_packages = [` 时括号不闭合，直接抛错。82 行正好是这个数组的起始行。
2. 守护进程的 IPC 只读了一次 socket（1024 字节）就去等下一次事件，而监听是边缘触发：`config.apply` 携带整份 TOML（约 2.2 KB）需要多次读取，剩下的字节再也等不到事件。于是**控制台每次保存都会把守护进程挂死**，客户端一直等回包——阈值当然「没生效」，连界面都像卡住。实测复现：`tempoctl apply` 10 秒超时，守护进程停在 `do_epoll_wait`，配置文件的 `config_generation` 不增加。
3. 控制台保存时按自己的字段表重新生成整份文件，会把 `[scene]`、`[fas]` 和 v3 新增的 `tier_table_max` 等字段整段丢掉。
4. 设备上还留着一份 v2 时代的旧配置，`profile_path` 指向已删除的 `babylon.toml`，且没有 `[scene]`。

**修复**：

- 守护端统一输出**极简规范形式**：单行数组、无尾随逗号、无行内注释、无注释头；`to_toml_string()` 写完后立刻反序列化并跑 `validate()`，产生不了合法文档就报错，绝不下发。
- 写配置改为「临时文件 → 回读校验 → 备份旧文件 → rename 覆盖」，任何一步失败都保留原文件，不会写坏。IPC 改为**循环读到 `WouldBlock` 为止**，多大的配置都能一次处理完，`config.apply` 立即返回 `{"ok":true,...}`。
- 守护启动时把地址不对的旧配置**就地规范化**（同时把 `profile_path` 钉到实际加载的 `device.toml`），所以设备上那份 v2 旧文件不用手动改。
- 控制台改为「文档保留式」读写：`parse → applyModel(只改界面暴露的字段) → stringify`，未暴露的字段原样保留；解析器同时兼容历史上出现过的跨行数组。

**验证**：

- 设备实际配置被改写为规范形式，`reading_packages` 等三行数组均为单行；第 82 行不再是数组起始。
- 修复后在设备上执行 `tempoctl apply --file`：**0 秒返回**，`config_generation` 从 1 递增到 2、3，守护进程日志出现 `charge reloaded after config.apply`，不再挂死。
- 用控制台同一份 `toml.js` 解析设备真实配置：9 个分组全部读出，场景包名 5/9/6 条，`[fas]` 保留；修改 `stop_at_percent` 后回写，`[scene]` 与 `[fas]` 未丢失，往返一致。

## 一、先看结论

这次把调度从「最低 / 最高两个档位来回跳」改成了**每簇一条 8 档的阶梯**，中间档位是真正会被用到的；同时彻底删掉了 v2.x 里那个会让手机卡开机的 bind-mount 方案。

已经做到：

- 包能刷入，结构和上一版一致，签名正式。
- 连续 5 次重启全部正常进系统，解锁后控制生效，没有白屏、没有卡第二屏。
- 开机守卫加强并通过人为破坏测试：故意把「已挂控制」的标记留下再重启，模块会自己生成 `disable` 并退出，频率回到官方状态；清掉 `disable` 再重启即恢复控制。
- 静态时三簇落在中间档（例：c0 787.2–902.4 MHz、c1 上限 1286.4 MHz、c2 上限 1478.4 MHz），不是硬件最低，也不是硬件最高。
- APP / WebUI 不再写死三簇，2 / 3 / 4 簇都能正确渲染；占用率是进入页面时用 0.5 秒固定窗口从 `/proc/stat` 真采样，不用随机数、不演示。
- 设备识别不到频率表时退化为「只读、不写」，不会写坏别人的手机。

**没有做到、也不宣称的：**

- 六个场景（小说静止 / 小说翻页 / 视频 / 输入法 / 长按倍速 / 冷启动）的 v3.0 实测功耗对比**没有测**。原因：按你的要求，设备侧实验（含压测、重启回归）在凌晨已全部停止，后续只做主机侧工作。所以本报告里凡是「是否低于官方功耗」，一律写「未测量」，不给结论。
- 因此 v3.0 目前的状态是：**功能与安全性已验证，功耗/流畅度的量化对照待你授权后补测。**

## 二、v2.x 到底哪里不对

用大白话说两个毛病。

### 毛病 1：像两个调度在打架

v2.x 在手机闲着的时候，把每簇的 min 和 max 都钉到硬件最低频，等于告诉系统「只许用这一档」。手指一碰屏幕，又把整簇放开到硬件最高。

结果就是你看到的：**静下来就是最低频，一动就是 3360 MHz，中间没有台阶**。系统被这样来回拽，既费电又卡顿，还容易和厂商自带的性能服务抢着写同一个文件。

一个正常的调度应该像开车：市区 40、环路 60、高速 100，按需要逐级换挡，而不是只有「停车」和「地板油」。

### 毛病 2：bind-mount 会在开机阶段卡死

v2.x 为了压住厂商对 `scaling_min_freq` 的改写，用 bind-mount 把一个假文件盖在真的上面。这个操作在开机早期、锁屏阶段做，会赶在系统初始化频率表之前，于是：

- 一次微信白屏；
- 一次卡在开机第二屏。

后来靠「解锁后 30 秒才挂」绕过去，但机制上仍然是脆的——只要时序变一点就会复发。

v3.0 里 **bind-mount 相关代码已经整体删除**（`mask.rs`、`maskbench.rs`、`mask_min.sh` 全部移除），不是关掉，是不存在了。

## 三、v3.0 怎么改的

### 3.1 阶梯调度：每簇 8 档，按需逐级走

启动时从 `/sys/devices/system/cpu/cpufreq/policy*/scaling_available_frequencies` 读真实频率表，等距抽成 **6–10 档（默认 8 档）**。之后所有决策都在这条阶梯上选一格，不再直接写硬件最低或最高。

选档依据两件事：

1. **负载**：每簇的 CPU 占用率（含前台进程占用），做指数平滑后映射到档位。用的是凹曲线——占用 3% 落在 1/7 档，15% 落在 2/7 档，40% 落在 4/7 档，不会一有负载就冲到顶。
2. **帧截止**：前台应用渲染超时（实际耗时 > 预算 + 余量）时，连续 3 次就把该簇临时推到顶档，持续一段时间再回落；如果是视频或阅读场景，则把「场景地板」整体抬高一级并保持到重启（在线自适应标定）。

防抖规则（这是「不打架」的关键）：

| 规则 | 值 | 作用 |
|---|---|---|
| 升档确认窗口 | 120 ms | 负载要持续这么久才真的升档，避免毛刺直接冲顶 |
| 单次最多升几档 | 2 档 | 事件路径不允许一步到顶 |
| 降档速率 | 45 ms / 档 | 一档一档退，不会瞬间砸到底 |
| 降档滞回 | 需低于目标 2 档，或回到 1 档，或已进入静默 | 防止在相邻两档之间反复横跳 |
| 上限前瞻 | 目标上方 3 档 | `scaling_max_freq` 永远给系统留出向上空间 |
| 上限安全带 | 阶梯的 35% | 任何情况下上限都不低于这个值，杜绝「被压到只能跑最低」 |
| 启动 / 掉帧 / 压力 | 上限全开 | 这三种时刻上限直接放开到硬件最高，恢复后再收 |

对外表现：运行时能看到 `tier 3/7`、`目标 787 MHz`、`上限 1094 MHz` 这种中间状态，而不是只有 0/7 两个值。

### 3.2 不再用 bind-mount，改成「写 min 目标 + 写 max 分档」

v3.0 的常态控制只做两件事：

- `scaling_min_freq` 写当前档位目标（让系统别掉到地板以下）；
- `scaling_max_freq` 写「目标 + 前瞻」的档位上限（让系统别乱冲顶），并保留 35% 安全带。

写序固定先 max 后 min，防止瞬时出现 `min > max` 被内核拒绝。

厂商的性能服务（perflock / QoS）有时会把 min 顶回来。v3.0 不跟它硬刚：连续被拒就 **30 秒退避**，期间不再重复写，也不和厂商互相拉扯；下一次对账（5 秒一次）再试。这是从「抢文件」改成「协商」。

锁屏、息屏、开机阶段：**零写入**。息屏时只把上限放开到硬件最高、目标置最低档，不做任何 min/max 强制。

### 3.3 地板按场景标定，不再一律压最低

| 场景 | 默认地板 | 触发条件 | 说明 |
|---|---|---|---|
| 视频 / 电视（B站、抖音、红果等） | 阶梯最低档 | 前台包名命中 `[scene].video` | 视频解码大多不在 CPU 上，所以默认给低地板；一旦出现超预算帧，场景地板自动 +1 档并保持，最多加到阶梯的 1/3，重启归零 |
| 小说阅读 | 阶梯最低档 | 命中 `[scene].reading` | 允许最低；翻页时走触摸路径，**只抬 1 档**，不整簇放开 |
| 输入法 | 见到输入法包名 | 命中 `[scene].ime` | 该簇目标封顶在阶梯的 45%，键盘弹出不许冲顶 |
| 长按倍速 / 按压屏幕 | —— | 持续触摸 | 只在非超大核上 +1 档；超大核完全不动，避免按压时大核冲顶 |
| 冷启动 / 切前台 | —— | `on_app_launch` / 前台变化 | 给 1200 ms 启动窗口，目标至少到阶梯 62%，上限全开；窗口结束后按负载正常回落 |

「视频零丢帧地板」的完整标定流程（逐档下降、每档连续 180 秒、记录码率与分辨率前提）需要真机长时间播放，本次**未执行**，见第九节待办。现在的实现是「保守低地板 + 掉帧自动抬一级」的在线自适应版本，先保证不卡，再谈省电。

### 3.4 通配任何处理器

v3.0 启动时会扫 `/sys/devices/system/cpu/cpufreq/policy*`，从里面推导：

- 簇数量（2 / 3 / 4 簇都能处理）；
- 每簇包含哪些 CPU（支持不连续编号，如 0–1、4–5）；
- 每簇可用频率表；
- 每簇 capacity（读 `cpu_capacity`，推大小核角色）；
- `cpuinfo_min_freq` / `cpuinfo_max_freq`。

识别不到、字段缺失、频率表少于 2 档，一律退化为 **只读模式**：不写任何频率文件，只在状态里报告。代码里原来写死 babylon（8 Gen 2）的 profile 已经删除，改为开机时由 `profile-gen.sh` 现场生成 `device.toml`；包里也不再带任何机型专用配置。

### 3.5 自身功耗

- 纯事件驱动：触摸、前后台切换、屏幕开关、帧回调、定时器到点才醒来，没有固定频率轮询。
- 静默后不再排定时器（`next_deadline()` 返回空），idle 时接近零唤醒。
- 对账间隔 5 秒，写操作间隔 30 ms，上限写入有 4% 死区，重复值直接跳过。
- 日志默认低量。
- 目标是守护进程 < 0.3% 单核。**这一项在 v3.0 上还没有重新测量**（v2.1.1 时代实测 0.38%，v3 去掉了更多轮询，预期更低，但没有数据就不写结论）。

### 3.6 APP / WebUI

- 簇数量完全来自 `status.clusters`：2 / 3 / 4 簇分别渲染 2 / 3 / 4 张卡片，CPU 区间按实际编号显示；没有数据时显示空态和「重新读取」，不伪造。
- 每簇占用率：进入页面或点刷新时，读两次 `/proc/stat`，间隔 0.5 秒（窗口用 `/proc/uptime` 实测校准），按簇聚合 `total` 与 `idle+iowait` 差值；界面标注「近 0.5s 采样」。只用真实数据，无随机数、无演示值、不做定时刷新。
- 每簇显示：角色、当前频率、目标频率、档位 `n/N`、上限、占用率、采样窗口。
- 全部页面与文案统一 v3.0，页脚固定 `Aegis · v3.0`。
- WebUI 已用本地浏览器分别以 2 / 3 / 4 簇渲染验证通过（见 `docs/v3.0-client.md`）。

### 3.7 充电控制

沿用原有沙盒模型（122 项用例已通过），未删功能、未改行为。本次不做真机验证。

## 四、开机守卫（三层，v3.0 加强）

1. **标记法**：`service.sh` 在拉起守护进程前写 `control.armed`。守护进程正常起来并完成 60 秒健康检查后，标记被清除。
2. **下次启动自检**：如果新的一次启动发现 `control.armed` 还在，说明上一次「挂了控制但没正常跑完」，立刻做三件事：
   - 卸载任何遗留的 v2 bind-mount；
   - `touch /data/adb/modules/aegis_scheduler/disable`（模块自我禁用）；
   - 退出，不启动守护进程。
3. **启动窗口只读**：守护进程起来后前 20 秒（`startup_guard_ms`）只读不写；`service.sh` 另外等待 `sys.boot_completed` + 解锁 + 30 秒冷静期才开始控制。开机和锁屏阶段零写入。

实测：人为留下标记重启 → 模块自动 `disable`、无 Aegis 进程、cpufreq 回到官方态（c0 672000–2016000）；移除 `disable` 再重启 → 恢复 v3 控制（pid 19675，c0 787200–902400）。

**直说结论**：

1. **是否比官方省电**：以均频作为功耗代理，静止场景三簇都低于官方；但放电电流在 USB 供电下**测不到**（MIUI 隐藏 `current now`，`current_now` 需 root 且被 SELinux 拦），所以我不宣称「实测功耗低于官方」，只能给出「静止均频更低」。
2. **是否比官方慢**：没有同口径的官方 jank 数据；本次 `dumpsys gfxinfo` 对 B 站、笔记、微信等第三方/系统应用都返回 `Failure while dumping the app`（MIUI 不允许非 debuggable 应用导出帧统计），**jank / p90 全部缺失，无法判定**。
3. **哪些没达标**：jank / p90 缺失；电流缺失；冷启动 3 个应用无耗时；Aegis 自身 CPU 在静止与翻页场景为 0.39%–0.46%，略高于 0.3% 单核目标（其余四场景 0.011%–0.017%）。

**这轮真正改掉的机制问题**（这是「两个调度打架」的根）：

- 厂商在每次触摸、每次启动后把 `scaling_min_freq` 抬到 787 / 1056 / 1248 MHz，且**不会自己降回去**。v3.0 现在只在「控制器判定该簇 idle 且处于最低档」时把地板拉回平台真实地板：实机为 **672 / 499 / 595 MHz**（c0 被平台 QoS 钳在 672，写 307 也会被抬回 672，守护会自动学习这个值，不再每 500 ms 重复写）。
- 正常控制**只写 `scaling_max_freq`**（上限），下限交给上面这条 idle 地板规则；不会出现「上一秒压到最低、下一秒冲最高」。
- 地板写入失败时按 0.5 s → 5 s 指数退避，不在触摸/启动窗口里和厂商对写。实测 40 分钟后台驻留，`floor_writes` 只增长 11 次，`writer.error=null`。

## 十、已知风险

1. **厂商 QoS 会顶 min**：本机 c0 手写 307200 常被顶回 672000。v3.0 的选择是退避不硬刚（30 秒），因此 c0 的地板实际由厂商决定。这是有意为之——硬刚就会重演「两个调度打架」。

# v3.0.3：自身开销与实测口径

- 日期：2026-11-09
- 设备：Xiaomi MIX Fold 3（kalama / 8 Gen 2），Android 16，KernelSU
- 状态：USB 充电、充电上限 50% 已生效、屏幕点亮停在锁屏／桌面静止

## 一、守护自身 CPU：改前 / 改后（同一台机、同一状态、各 60 s）

测法：`/proc/<pid>/task/*/schedstat` 逐线程累加得到 ns 级在 CPU 时间，`/proc/<pid>/status` 取
voluntary + nonvoluntary 切换数；同一设备状态（亮屏、无输入、静态界面）下先后跑官方对照版
（v3.0.2 二进制）与本版，中间只换二进制，其余完全一致。

| 版本 | 窗口 | 在 CPU 时间 | 单核占用 | 上下文切换 | 切换/秒 |
|---|---|---|---|---|---|
| v3.0.2 | 60.10 s | 285 ms | 0.474 % | 724 | 12.0 |
| v3.0.3 | 60.11 s | 185 ms | 0.308 % | 666 | 11.1 |
| v3.0.3（熄屏） | 60.00 s | 6 ms | ≈0.01 % | 6 | 0.1 |

- 亮屏静止下降 **35 %**（0.474 % → 0.308 %），切换数下降 **8 %**。
- 熄屏几乎没有唤醒，说明剩余开销集中在亮屏时的采样路径，而不是定时器空转。
- 距「≤0.3 %」还差一点点（0.308 %），如实记录，不四舍五入成达标。

### 改了什么

1. **热区采样 1.5 s → 6 s**：热区每个 `thermal_zone*/temp` 都是一次 QMI 事务。安静且不热时
   放宽到 6 s；一旦温度进入 `guard-3 °C` 以内或出现交互，立刻回到 1.5 s，安全阈值不变。
2. **每次采样少一次加锁、少一次克隆**：原先 `record()`、`update_usage()`、`commit()` 各锁一次
   状态，`decisions` 还被克隆两次。现在 usage 平滑并入 `record()`，`decisions` 只由 `commit()`
   写一次；`idle` 采样直接跳过向量拷贝。
3. **涓流锁存后不再 3 s 一拍**：100 % 涓流阶段原本每 3 s 读一次电流并写一条 INFO 日志；锁存后
   证据已足够，改为 30 s 复查，且只有锁存状态翻转时才写 INFO，其余降为 DEBUG。
4. **epoll EINTR 不再杀死守护**：`epoll_wait` 被信号打断（SIGCHLD、ptrace 附着等）时原实现直接
   退出并交还 cpufreq；现在原地重试。这一条是实测中真实触发过的（attach 调试时守护退出）。

## 二、jank / p90：**本版缺失**

- 计划口径：`atrace`/`perfetto` 以 root 抓 `gfx`、`view`、`sched`、`freq`，每段 ≤20 s，
  用 `Choreographer#doFrame` 的 B/E 对与帧间隔判定超预算帧（60 fps 16.7 ms / 30 fps 33.3 ms），
  统计 jank 率与 p90。工具链已验证可用（本机 `perfetto`、`atrace` 均在，5 s 试抓能拿到
  `Choreographer#doFrame` 与 `FrameTimeline` 标记）。
- 为什么没有数：设备重启后停在锁屏，`/sdcard` 与第三方应用都处于未解锁（CE 未解密）状态，
  `am start` 无法把小说/B站/抖音拉到前台。已按授权用 `input -d 1 swipe` + `input text` 走密码解锁，
  但这块 ROM 的锁屏不接受 adb 注入的上滑（密码盘始终不出现），截屏时亮时黑，无法确认输入焦点；
  **解锁状态不是我能绕过的，我没有改任何系统开关去绕。** 没有前台应用就没有可统计的帧，
  只能空跑。**没有拿别的场景冒充这五项。**
- 补充：本机 `input -d 1` 已确认指向外屏（1080×2520，state ON），事件能到达但锁屏不响应；
  内屏（1916×2160）处于 OFF，因此不存在“发错屏”的解释。
- 也未做官方对照：模块 disable + 一次重启这条路径必须先经你同意。

真实放电电流要拔掉 USB 才能测；本轮全程插着线（充电上限 50 % 正在工作），测到的只会是充电
曲线。没有拔线、也没有动充电状态，等你的答复。
